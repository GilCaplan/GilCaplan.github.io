VirtualHome PDDL Task Solver

Household agent tasks solved by combining an LLM with classic PDDL planning, then executed in the VirtualHome simulator.

PDDL planning Gemini 1.5 Flash VirtualHome simulator unified_planning / pyperplan auto MP4 + verification

The idea

An autonomous household agent in the VirtualHome simulator has to carry out natural-language tasks like "Wash teeth" or "Put groceries in the fridge". Instead of hard-coding task-specific scripts, this system routes everything through structured PDDL planning: the live scene graph becomes a PDDL problem, a planner produces an action plan, and that plan is translated into executable VirtualHome commands, run with frame recording, and verified.

The repo contains two solver paths over the same PDDL domain:

  • LLM planner (llm_planner.py) — Gemini 1.5 Flash infers the goal from the task description and emits a plan, with a validation + retry loop.
  • Classic planner (test_planner.py) — the unified_planning library solves the domain+problem with the pyperplan engine; the modular pipeline calls this path (run_unified_planner_string). A vendored Fast Downward is also included.

So the loop is genuinely LLM ↔ classic PDDL: the LLM handles language understanding and goal/scene grounding; the symbolic planner handles sound, typed action sequencing. Either path produces a plan the converter turns into a VirtualHome script.

The PDDL domain

The agent's whole action space is defined as a typed STRIPS domain. Object types form a hierarchy and reachability is modelled explicitly (on a surface, inside a container, inside a room, or always-reachable).

Types

objectt, agent, room
 ├─ sittable-objectt
 ├─ switchable-objectt
 ├─ grabbable-objectt
 └─ static-objectt
     ├─ surface-objectt
     └─ container-objectt

Key predicates

(at ?agent ?room)
(sitting ?agent) (standing ?agent)
(holding ?agent ?obj)
(close ?agent ?obj)
(has-free-hand ?agent)
(on ?appl) (off ?appl)
(is-open ?cont) (is-closed ?cont)
(reachable-on-surface ?obj ?surf)
(in-container ?obj ?cont)

How the LLM is prompted (from llm_planner.py)

      
The Gemini path builds a prompt with the task, the available rooms, and each scene object's
      capabilities, then constrains it to exact action names and includes goal-inference examples:

      
"Write an email"      → Goal: agent sitting at computer, computer ON
"Put groceries in fridge" → Goal: fridge opened, items inside, fridge closed
"Watch TV"            → Goal: agent sitting, TV ON
"Go to sleep"         → Goal: agent in bedroom, on bed

      
The generated plan is then validated (_validate_pddl_plan):
      every action must be one of 10 known action names with the right arity, and type checks reject
      e.g. switch-on on a non-switchable object — on failure the prompt
      is tightened and retried (up to 3 attempts).

    

    
No real Output/ mp4 or generated plan files are committed
    to the repo (that folder is git-ignored), so the example above reflects the README's documented
